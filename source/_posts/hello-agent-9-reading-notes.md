# 面试速记

## 一句话概括

第九章讲的是 **Context Engineering（上下文工程）**：在每一次模型调用前，如何系统地筛选、组织、压缩和补充上下文，让 Agent 在长任务、多工具、多轮交互中保持稳定、聚焦和可控。

## 背诵版总结

上下文工程可以理解为提示工程的进一步升级。提示工程主要关注“怎么写好提示词”，而上下文工程关注的是“模型在一次调用时应该看到哪些信息”。在 Agent 场景中，模型不仅需要系统提示，还需要工具描述、历史消息、外部数据、检索结果、项目状态、结构化笔记等信息。由于上下文窗口和模型注意力都是有限资源，信息越多并不一定越好，过长上下文反而可能带来上下文腐蚀，使模型更难准确提取关键信息。因此，上下文工程的核心目标是：在有限 token 预算内，提供高信号密度、低噪声、结构清晰的上下文。

本章从理论和实践两个层面介绍上下文工程。理论上，它强调注意力预算、上下文腐蚀、有效上下文的组成，以及面向长时程任务的三种策略：压缩整合、结构化笔记和子代理架构。实践上，HelloAgents 新增了 ContextBuilder、NoteTool 和 TerminalTool。ContextBuilder 实现 GSSC 流水线，即 Gather、Select、Structure、Compress，用统一流程完成上下文获取、选择、结构化和压缩；NoteTool 用 Markdown + YAML 记录长期任务状态、结论、阻塞和行动项；TerminalTool 让 Agent 能够即时访问文件系统，实现 Just-in-time 上下文检索。最后，本章把这三者结合成代码库维护助手，展示长程智能体如何在上下文窗口有限的情况下完成代码库探索、问题记录和持续重构建议。

## 面试表达模板

如果面试官问“你怎么理解上下文工程”，可以这样回答：

> 我理解上下文工程是提示工程在 Agent 场景下的扩展。提示工程主要解决“指令怎么写”，而上下文工程解决“每次调用模型时应该给模型看什么”。在复杂 Agent 系统中，输入上下文不仅包括系统提示，还包括工具说明、历史对话、检索结果、外部文件、结构化记忆和当前任务状态。由于上下文窗口和注意力预算有限，并且长上下文会出现上下文腐蚀，所以不能简单把所有信息都塞给模型，而要进行筛选、排序、结构化和压缩。第九章中 HelloAgents 用 ContextBuilder 实现了 Gather、Select、Structure、Compress 的 GSSC 流水线，并结合 NoteTool 和 TerminalTool 支持长期任务记录和即时文件系统检索。这说明一个稳定的 Agent 系统不仅要有模型和工具，还要有系统化的上下文管理能力。

# Hello-Agent 第九章：上下文工程阅读笔记

## 1. 本章核心内容

第九章《上下文工程》围绕一个核心问题展开：

> 在每一次大语言模型调用之前，应该如何构造最合适的上下文？

前面章节已经介绍了记忆系统和 RAG，但真实 Agent 系统只靠记忆和检索还不够。因为 Agent 在执行长任务时，会不断产生新的信息，例如：

- 用户目标；
- 历史消息；
- 工具调用结果；
- 检索证据；
- 文件路径；
- 项目状态；
- 中间结论；
- 待办事项；
- 错误和阻塞点。

这些信息不可能全部无差别塞进上下文窗口。上下文工程要解决的就是：**如何从不断扩张的信息集合中，选出最有价值的信息，并以合适结构提供给模型。**

本章主要包括四部分：

1. 上下文工程的概念和必要性；
2. 有效上下文的组成和长时程任务策略；
3. HelloAgents 中的 ContextBuilder、NoteTool、TerminalTool；
4. 长程智能体案例：代码库维护助手。

---

# 2. 什么是上下文工程？

## 2.1 从提示工程到上下文工程

提示工程关注的是：

```text
如何写好 Prompt？
```

例如：

- 系统提示怎么写；
- 角色设定怎么写；
- 输出格式怎么约束；
- few-shot 示例怎么设计。

而上下文工程关注的是：

```text
模型在一次调用时，应该看到哪些信息？
```

也就是说，上下文工程的范围比提示工程更大。它不仅包括 prompt，还包括所有会进入上下文窗口的信息：

- 系统提示；
- 用户问题；
- 历史对话；
- 工具列表；
- 工具返回结果；
- RAG 检索片段；
- 结构化记忆；
- 文件内容；
- 当前任务状态；
- 输出格式约束。

因此，提示工程更像“写指令”，上下文工程更像“搭建模型可见的信息环境”。

## 2.2 上下文工程的核心定义

上下文工程可以理解为：

> 在 LLM 调用前，以可复用、可度量、可演进的方式，拼装、筛选、组织和压缩输入上下文，从而提升模型输出的正确性、鲁棒性和效率。

它的目标不是让上下文越长越好，而是让上下文：

- 更相关；
- 更清晰；
- 更紧凑；
- 更结构化；
- 更容易被模型利用。

## 2.3 为什么 Agent 特别需要上下文工程？

普通问答可能只需要一次模型调用，但 Agent 往往是循环运行的：

```text
思考 -> 调用工具 -> 观察结果 -> 更新状态 -> 再思考
```

每一轮都会产生新信息。如果不加管理，上下文会越来越长，最终导致：

- 关键信息被淹没；
- 模型注意力分散；
- 工具结果重复堆积；
- 历史消息噪声增加；
- 模型开始遗漏目标或偏离任务。

因此，Agent 越复杂，越需要上下文工程。

# 3. 为什么上下文工程重要？

## 3.1 上下文是有限资源

很多人会误以为模型上下文窗口越大越好，实际并不是这样。即使模型支持很长的上下文，也不代表模型能稳定、准确地利用所有信息。

上下文窗口可以变大，但模型的“注意力预算”仍然有限。每增加一个 token，都会占用模型注意力的一部分。如果上下文中无关信息过多，模型就更难关注真正重要的内容。

## 3.2 上下文腐蚀

本章提到一个重要现象：**context rot，上下文腐蚀**。

它指的是：随着上下文长度增加，模型从上下文中准确回忆和利用关键信息的能力可能下降。

这和人类工作记忆类似。给一个人太多材料，他不一定表现更好，反而可能因为信息过载而忽略重点。

## 3.3 Transformer 架构带来的限制

Transformer 中，每个 token 都会和其他 token 建立注意力关系。理论上，token 之间存在大量两两关系。上下文越长，模型越难对所有信息保持同样精确的关注。

因此，长上下文并不是免费的能力。上下文工程要做的事情，就是帮助模型减少无效信息，把有限注意力放在关键内容上。

# 4. 有效上下文的组成

本章强调，有效上下文不是“越多越好”，而是“信息充分但紧致”。

一个高质量上下文通常包括三个核心组成：

1. 系统提示；
2. 工具；
3. 示例。

## 4.1 系统提示

系统提示负责定义 Agent 的身份、目标、规则和输出要求。

好的系统提示应该：

- 语言清晰；
- 规则明确；
- 层次分明；
- 不过度硬编码；
- 不过于空泛；
- 包含必要背景和输出约束。

常见问题有两类：

### 1. 过度硬编码

如果在提示词里写大量脆弱的 if-else 规则，后续维护成本会很高，而且模型也未必能稳定遵守。

### 2. 过于空泛

如果只写“你是一个有帮助的助手”，却没有说明任务背景、工具用法和输出标准，模型就缺少可执行信号。

更好的做法是用 Markdown 或 XML 分区组织，例如：

```text
[Role & Policies]
[Task]
[State]
[Evidence]
[Context]
[Output]
```

## 4.2 工具

工具定义了 Agent 和外部世界交互的方式。

高质量工具应该满足：

- 职责单一；
- 功能边界清楚；
- 输入参数明确；
- 返回结果简洁；
- 错误处理鲁棒；
- 工具之间低重叠。

如果工具集过于臃肿，模型会不知道该调用哪个工具。  
所以工具设计不是越多越好，而是要构建最小可行工具集。

## 4.3 示例

few-shot 示例可以直接告诉模型“什么是好行为”。

但示例也不能无限堆叠。  
应该选择少量典型、多样、有代表性的示例，而不是把所有边界条件都塞进去。

好的示例能帮助模型更稳定地学习输出格式、判断标准和推理风格。

# 5. 上下文检索与智能体式搜索

## 5.1 从一次性检索到 JIT 上下文

传统 RAG 常见做法是：

```text
用户问题 -> 向量检索 -> 拼接片段 -> 生成答案
```

这种方式适合简单问答，但对于复杂任务还不够灵活。

本章提出的方向是：**Just-in-time Context，即即时上下文**。

它不是提前把所有资料都放入上下文，而是让 Agent 保留轻量级引用，并在需要时通过工具动态获取信息。

例如：

- 文件路径；
- URL；
- 数据库查询；
- 目录结构；
- 日志文件位置；
- 项目说明文档。

模型需要时再调用工具查看具体内容。

## 5.2 JIT 上下文的价值

JIT 上下文的优势是：

1. 不需要一次性加载全部信息；
2. 可以保持上下文轻量；
3. 可以获取最新文件内容；
4. 可以逐步探索复杂信息空间；
5. 更接近人类使用文件系统和搜索工具的方式。

例如开发者理解一个代码库时，也不会把所有文件一次性读完，而是先看目录结构，再按需查看关键文件。

## 5.3 渐进式披露

JIT 上下文带来一个重要能力：**渐进式披露**。

Agent 可以一步一步获取信息：

```text
先看目录 -> 再看文件名 -> 再看关键文件 -> 再 grep 具体函数 -> 再读取片段
```

每一步的新发现都会指导下一步搜索。

这种方式比“预先塞入全部材料”更高效，也更不容易造成上下文污染。

# 6. 面向长时程任务的上下文工程

长时程任务指的是那些需要跨很多轮、甚至跨多次会话持续推进的任务，例如：

- 大型代码库重构；
- 长时间研究任务；
- 项目规划与跟踪；
- 多阶段数据分析；
- 复杂系统排障。

这类任务无法依靠单次上下文完成，需要专门的上下文管理策略。

本章提出三种重要策略：

1. 压缩整合；
2. 结构化笔记；
3. 子代理架构。

## 6.1 压缩整合 Compaction

压缩整合是指：

> 当上下文接近上限时，对历史对话和工具结果进行高保真总结，用摘要重启新的上下文窗口。

它保留：

- 架构性决策；
- 关键结论；
- 未解决问题；
- 实现细节；
- 当前进度；
- 下一步计划。

它丢弃：

- 重复工具输出；
- 低价值闲聊；
- 已解决的临时信息；
- 噪声性中间过程。

压缩整合适合需要“上下文接力”的长对话任务。

## 6.2 结构化笔记 Structured Note-taking

结构化笔记是让 Agent 把关键信息写入上下文外部的持久存储。

例如：

- TODO 列表；
- NOTES.md；
- 阶段性结论；
- 阻塞问题；
- 关键决策；
- 参考资料。

这样即使当前上下文被压缩或重置，Agent 仍然可以通过笔记恢复长期状态。

结构化笔记适合迭代式开发和研究任务。

## 6.3 子代理架构 Sub-agent Architectures

子代理架构是指：

```text
主代理负责高层规划和综合
子代理负责局部探索和深挖
子代理最终只返回凝练摘要
```

这样可以把复杂搜索过程隔离在子代理自己的上下文窗口中，避免主代理被大量细节污染。

它适合：

- 复杂研究；
- 并行信息探索；
- 多方向分析；
- 大规模资料筛选。

# 7. ContextBuilder：上下文构建器

## 7.1 ContextBuilder 的核心作用

ContextBuilder 是 HelloAgents 中用于上下文工程的核心组件。

它实现了 GSSC 流水线：

```text
Gather -> Select -> Structure -> Compress
```

中文可以理解为：

```text
获取 -> 选择 -> 结构化 -> 压缩
```

它的目标是把上下文管理从零散代码变成统一、可复用的工程流程。

## 7.2 Gather：获取上下文候选

Gather 阶段负责收集所有可能相关的信息，例如：

- 用户任务；
- Agent 状态；
- 历史对话；
- 记忆内容；
- RAG 证据；
- 工具返回结果；
- 外部笔记。

这一步不是马上全部放入 prompt，而是先形成候选上下文池。

## 7.3 Select：选择高价值信息

Select 阶段根据相关性和新近性选择最重要的信息。

本章中 ContextBuilder 的设计理念是简单高效，统一用：

```text
相关性 + 新近性
```

进行评分。

这样可以优先保留：

- 与当前任务高度相关的信息；
- 最近出现的重要信息；
- 高优先级状态；
- 当前未解决的问题。

## 7.4 Structure：结构化组织

Structure 阶段把选中的信息组织成稳定模板。

本章提到的上下文骨架包括：

```text
[Role & Policies]
[Task]
[State]
[Evidence]
[Context]
[Output]
```

这种结构有几个好处：

- 模型更容易理解信息层级；
- 调试更方便；
- 便于 A/B 测试；
- 方便观察不同上下文模块对结果的影响。

## 7.5 Compress：压缩兜底

当上下文超出 token 预算时，Compress 阶段负责压缩。

压缩不是简单截断，而是尽量保留高价值内容，把低价值、重复、过长的信息压缩成摘要。

这能保证系统在长任务中不会因为上下文过长而失败。

## 7.6 ContextBuilder 的最佳实践

使用 ContextBuilder 时需要注意：

- 根据任务复杂度动态调整 token 预算；
- 生产环境可用向量相似度替代简单关键词重叠；
- 对稳定内容做缓存；
- 记录上下文构建日志；
- 对相关性权重和新近性权重做 A/B 测试。

# 8. NoteTool：结构化笔记

## 8.1 NoteTool 的定位

NoteTool 是为长时程任务提供的结构化外部记忆组件。

它使用：

```text
Markdown 正文 + YAML 元数据
```

来记录长期任务信息。

这种设计既适合机器解析，也适合人类阅读和版本管理。

## 8.2 为什么需要 NoteTool？

第八章中的 MemoryTool 更偏对话式记忆，比如工作记忆、情景记忆和语义记忆。  
而 NoteTool 更适合项目式、阶段性、长期跟踪的任务。

它可以记录：

- 当前任务状态；
- 阶段性结论；
- 阻塞问题；
- 下一步行动；
- 参考资料。

## 8.3 NoteTool 的存储格式

一个笔记通常包括 YAML 前置元数据：

```yaml
---
id: note_20250119_153000_0
title: 项目进展 - 第一阶段
type: task_state
tags: [refactoring, phase1, backend]
created_at: 2025-01-19T15:30:00
updated_at: 2025-01-19T15:30:00
---
```

正文则用 Markdown 记录具体内容。

这种格式的优点是：

- YAML 方便检索和机器解析；
- Markdown 方便人类阅读和编辑；
- 文件天然支持 Git 版本管理；
- tags 和 type 可以做多维度检索。

## 8.4 NoteTool 的核心操作

NoteTool 支持笔记生命周期管理，例如：

- create：创建笔记；
- read：读取笔记；
- update：更新笔记；
- delete：删除笔记；
- list：列出笔记；
- search：检索笔记；
- archive：归档笔记。

它让 Agent 能够像人一样维护项目笔记，而不是只依赖临时上下文。

## 8.5 NoteTool 与 ContextBuilder 的结合

NoteTool 的价值在于可以和 ContextBuilder 配合：

```text
NoteTool 负责长期记录
ContextBuilder 负责按需选择并注入相关笔记
```

例如，在每轮对话前，Agent 可以检索与当前任务相关的 blocker、action、conclusion，再由 ContextBuilder 按优先级放入上下文。

这让 Agent 能够跨会话保持一致性。

# 9. TerminalTool：即时文件系统访问

## 9.1 TerminalTool 的定位

TerminalTool 为 Agent 提供安全的命令行执行能力，让 Agent 可以即时访问文件系统。

它体现的是 JIT 上下文思想：

> 不提前把所有文件加载到上下文中，而是让 Agent 根据任务需要逐步探索。

## 9.2 TerminalTool 适合的场景

TerminalTool 适合：

- 代码库探索；
- 日志分析；
- 数据文件预览；
- 配置文件检查；
- 文件结构理解；
- 按需 grep、head、tail。

例如理解代码库时，Agent 可以先执行：

```bash
find . -name '*.py' -type f
```

再根据文件名选择关键文件：

```bash
grep -r 'class UserService' .
```

最后只读取相关片段：

```bash
head -n 50 src/services/user.py
```

## 9.3 TerminalTool 的价值

TerminalTool 的优势是：

- 获取实时文件内容；
- 不依赖预先索引；
- 减少无关上下文；
- 支持渐进式探索；
- 更适合动态代码库和日志场景。

## 9.4 安全机制的重要性

因为 TerminalTool 能执行命令，所以必须有安全限制，例如：

- 限制工作目录；
- 命令白名单；
- 超时控制；
- 禁止危险命令；
- 控制输出长度；
- 避免敏感信息泄露。

这说明工具能力越强，越需要边界控制。

# 10. 长程智能体实战：代码库维护助手

## 10.1 案例目标

本章最后把 ContextBuilder、NoteTool、TerminalTool 和 MemoryTool 结合起来，构建了一个代码库维护助手。

这个助手能够：

1. 探索和理解代码库结构；
2. 记录发现的问题和改进点；
3. 追踪长期重构任务；
4. 在上下文窗口限制下保持任务连贯性。

## 10.2 面临的核心挑战

代码库维护助手面对三个典型挑战：

### 1. 信息量超出上下文窗口

一个中型代码库可能有几十个文件、几万行代码，不可能全部放入上下文。

解决方式：

```text
用 TerminalTool 即时探索，只读取当前需要的文件和片段。
```

### 2. 跨会话状态管理

重构任务可能持续数天甚至数周，不能靠单轮对话记住全部状态。

解决方式：

```text
用 NoteTool 记录阶段进展、待办事项、关键决策和阻塞问题。
```

### 3. 上下文质量控制

每次对话都需要回顾历史，但不能被无关信息淹没。

解决方式：

```text
用 ContextBuilder 按相关性和新近性筛选上下文。
```

## 10.3 三层架构理解

代码库维护助手可以理解为三层：

### 1. 工具层

包括：

- TerminalTool：查看文件、搜索代码、分析日志；
- NoteTool：记录长期状态；
- MemoryTool：保存语义记忆和情景记忆。

### 2. 上下文管理层

由 ContextBuilder 负责，把当前任务、历史状态、相关笔记和检索证据组织成高质量上下文。

### 3. Agent 决策层

由 LLM 驱动，根据上下文进行推理、生成建议、规划下一步操作。

# 11. 本章核心启发

## 11.1 上下文工程比提示词更接近生产问题

在真实 Agent 系统中，问题往往不是“prompt 写得不够好”，而是模型看到的信息不对：

- 关键信息没放进去；
- 无关信息放太多；
- 工具结果太长；
- 历史状态不清；
- 输出格式缺少约束。

因此，上下文工程是 Agent 工程化的关键。

## 11.2 上下文不是越长越好

长上下文可以容纳更多信息，但也可能带来噪声、注意力分散和上下文腐蚀。

高质量上下文应该是：

```text
相关性高
结构清楚
信息密度高
token 开销低
```

## 11.3 长程任务必须依赖外部记忆

如果任务持续时间很长，单靠模型上下文是不够的。  
必须把重要状态写入外部系统，例如：

- 结构化笔记；
- 向量记忆；
- 项目文件；
- 数据库；
- TODO 列表。

## 11.4 JIT 上下文适合真实工程场景

真实项目中的文件、日志和代码经常变化。  
预先索引全部内容成本高，也可能过时。  
JIT 上下文让 Agent 像开发者一样按需探索，是更灵活的方式。

## 11.5 ContextBuilder 是上下文工程的统一接口

GSSC 流水线把上下文管理拆成清晰步骤：

```text
Gather：收集候选信息
Select：选择高价值信息
Structure：组织成固定结构
Compress：超限时压缩
```

这让上下文管理从“临时拼 prompt”变成可维护的工程模块。

# 12. 面试高频问题

## Q1：上下文工程和提示工程有什么区别？

提示工程关注如何写好指令，重点是 prompt 的表达方式。上下文工程关注每次模型调用时应该给模型哪些信息，范围包括系统提示、工具描述、历史消息、检索结果、记忆、文件内容和任务状态。因此，上下文工程是提示工程在复杂 Agent 场景下的扩展。

## Q2：为什么上下文不是越长越好？

因为模型的上下文窗口和注意力预算有限。上下文越长，无关信息越多，模型越可能忽略关键内容，出现上下文腐蚀。因此好的上下文应该追求高信号密度，而不是简单堆叠信息。

## Q3：什么是 GSSC 流水线？

GSSC 是 ContextBuilder 的上下文构建流程，包括 Gather、Select、Structure、Compress。它先收集候选上下文，再选择高价值信息，然后组织成稳定结构，最后在超出 token 预算时进行压缩。

## Q4：NoteTool 和 MemoryTool 有什么区别？

MemoryTool 更偏对话式记忆，适合保存工作记忆、情景记忆和语义记忆。NoteTool 更偏项目式长期记录，使用 Markdown + YAML 保存任务状态、结论、阻塞和行动项，适合长程任务和跨会话状态管理。

## Q5：TerminalTool 为什么体现 JIT 上下文？

TerminalTool 允许 Agent 按需访问文件系统和命令行，不需要提前把所有文件塞进上下文。Agent 可以先看目录，再 grep 关键内容，最后只读取相关片段，这就是 Just-in-time 上下文。

## Q6：长程智能体为什么需要压缩整合？

因为长程任务会产生大量历史消息和工具结果，最终超过上下文窗口。压缩整合可以把历史信息总结成高保真摘要，保留关键决策、进度和问题，再用新的上下文窗口继续任务。

# 14. 总结

第九章的核心不是单纯增加一个工具，而是提出一种 Agent 工程化思维：**模型能力再强，也需要高质量上下文才能稳定发挥作用。**

上下文工程关注的是模型在每次调用时看到的完整信息环境。它要求我们把系统提示、工具、示例、历史、记忆、检索结果和外部文件统一管理起来，并在有限 token 预算内保留最有价值的信息。

本章通过 ContextBuilder、NoteTool 和 TerminalTool 展示了一个完整方案：

```text
ContextBuilder 负责上下文构建
NoteTool 负责长期结构化记忆
TerminalTool 负责即时文件系统检索
```

三者结合后，Agent 不再只是一个能回答问题的聊天模型，而是能够在长时程任务中持续探索、记录状态、管理上下文并稳定推进目标的工程化系统。
